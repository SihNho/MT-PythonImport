# iXon Ultra at 50 fps, EM gain 0, 1 min: not reached, stopped as instructed (2026-10-30)

Owner (relayed by the main session, verbatim): "현재 EMCCD 전원은 켜뒀음. EM gain 0으로 acquisition 해볼 것. 50 fps, 1 min."
Instruction with it: use frame transfer ON for 50 fps; if 50 fps cannot be reached, stop and report the reachable
maximum, never substitute a lower rate. Runs inside V6 `tools/rig_session.py --no-motor-session` (the first launch
was refused because another session held the lock for the rotor job; the wrapper waited and ran at 09:35:17; lock
released after each run). Nothing moved. Tool: `tools/emccd_acq.py` (frame transfer on, gain mode 0, gain 0, rate
50 Hz; reads the SDK ring, counts frame-number jumps as loss, samples the sensor temperature every 10 s).

## What happened

| step | result |
|---|---|
| connect, frame transfer on | readout time measured 21.05 ms (shortest period with the exposure at 0) |
| rate 50 Hz | **refused before anything was sent**: `emccd rate 50.0 Hz is outside [0.01, 47.506] Hz (1 / readout 21.05 ms, frame transfer on)` |
| acquisition | not started (the tool stops when the requested rate is not reached) |
| cleanup | disconnected: cooler off, ShutDown; rig_session: job gone, no LabVIEW, lock released |

So the 1 min run was **not done**: nothing on frames received, loss, temperature during a run or mean counts at 50 fps.
Reachable maximum at the current readout set-up: **47.5 fps** (period 21.05 ms).

## Why, and what would reach 50 fps (owner's decision)

Readout speeds read from the camera on the next open (09:36, same session set-up):

| item | value |
|---|---|
| horizontal (HS) speeds, EM amplifier | 17.0, 10.0, 5.0, 1.0 MHz; **in use: 17.0 MHz** (index 0, already the fastest) |
| vertical shift (VS) speeds | 0.3, 0.5, 0.9, 1.7, 3.3 us per row; **in use: 3.3 us** (index 4, `GetFastestRecommendedVSSpeed`, the slowest) |

At 512 rows the vertical shift costs 512 x 3.3 us = 1.7 ms per shift, twice per frame in frame-transfer mode (the
frame transfer and the readout's own row shifts), on top of 512 x 512 / 17 MHz = 15.4 ms of horizontal readout.
A faster VS speed (0.5 us: 0.26 ms per shift) brings the period to about 18 ms, i.e. about 55 fps, which matches
the 897's data sheet (56 fps full frame). The driver sets the "fastest recommended" VS speed as smCamera did
(`docs/manuals/smcamera-emccd-parameters.md`); a faster one is allowed by the SDK but may need the VS clock
amplitude raised (`SetVSAmplitude`) and can add clock-induced charge. **Options:** (a) 47.5 fps now, same set-up;
(b) VS speed 0.5 us (or 0.3 us) and 50 fps; (c) a smaller ROI or 2 x 2 binning at 50 fps. The owner picks; the
driver gets a `vs_speed` (and `roi`) setting then.

## Shutter (owner 2026-10-30: "SetShutter로 하는거 맞을듯. 전에 EMCCD 사용했을 때는 항상 셔터 오픈 먼저하고 acquisition 했음.")

Read from the camera (09:38): `IsInternalMechanicalShutter` = 1, capability bits `AC_FEATURES_SHUTTER` and
`AC_FEATURES_SHUTTEREX` set: **this iXon has an internal mechanical shutter**. `SetShutter(1, mode, 0, 0)` and
`(1, mode, 10, 10)` were refused with 20068 (`DRV_P3INVALID`, the closing time); `SetShutter(1, mode, 50, 50)` and
`SetShutterEx(1, mode, 50, 50, 0)` are accepted (Andor's example values; smCamera used 1 ms, which this SDK refuses).
So in every run before 09:39 the shutter was never commanded and stayed at the `Initialize` default (closed): the
owner heard no click, and the snaps' mean of about 200 counts is the bias level. The 4.4 LabVIEW VI's wiring was not
read (binary; no LabVIEW file touched).

Now in the driver: shutter closed at open; `start()` / an acquisition start opens it first (as the LabVIEW program
did), `stop()` and the disconnect close it; `shutter` is also a setting (0 auto, 1 open, 2 closed). Never auto in
run-till-abort: the SDK then adds both 50 ms transfer times to every frame (readout measured 124.59 ms instead of
24.59 ms). Probe 09:41 (EM gain 0, 30 ms, 18 Hz, no illumination set up): snap mean **203.7 shutter open / 202.5
closed / 199.9 open again** (min about 120, max 270-390): no measurable light reached the sensor either way, so
whether light arrives with the shutter open still has to be checked with the illumination on. The shutter commands
are accepted and read back; the click itself was not verified (nobody at the rig).

The 50 fps 1 min run with the shutter open still waits for the owner's choice above (47.5 fps max at VS 3.3 us).
