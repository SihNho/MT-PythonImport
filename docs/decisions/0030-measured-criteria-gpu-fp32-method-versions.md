# 0030 - Tracking methods are chosen by measurement; the GPU path is FP32 and free of the LabVIEW numbers; method names carry versions; user reports are HTML

**Decided:** 2026-11-07 (owner, in a side chat pasted into the main session at ~02:20; the paste is the record).
Amends 0003 / 0004 / 0008 (numbers identical to LabVIEW), 0023 item 4 and 0024 (three Z methods on numba and CUDA).

## What the owner decided
1. **"If the precision is better than LabVIEW's analysis, adopting it is rational."** The identity rule stays only
   on the reference: `current_v1` on numba FP64 reproduces the LabVIEW numbers (single-precision sums,
   round-half-even, the out-of-range index) and its tests stay. Every other method / executor is judged by
   measurement against that reference. The LabVIEW method stays an option for good ("so my experiments keep their
   continuity; the data taken with LabVIEW cannot be thrown away"); `.cal` / `.tra` stay as they are.
2. **The GPU does not keep to the LabVIEW arithmetic** ("the computation changes anyway"): the CUDA path is designed
   around FP32 (mixed precision where a stage needs it: the radial accumulation, the 3 x 3 solve), with the
   algorithm choices that suit it (FFTs, interpolation), and is adopted on the measured criteria. The FP64 CUDA
   kernel of 0024 stays as the "cuda fp64" baseline in the tables; its 11-01 and 11-07 rows are superseded for the
   FP32 path and kept for the comparison.
3. **The CPU `spline` / `phase_spline` are improvable too** (interpolation order, search range, convergence and
   fallback conditions, the tail of the per-frame time); they were never LabVIEW's, so the identity rule never
   applied to them.
4. **Method names carry a version**: `current_v1`, `spline_v1`, `phase_spline_v1` are today's implementations; a
   change that alters the numbers (algorithm, interpolation, precision) raises the number, a change that only
   speeds things up does not (the 11-07 GPU kernel trim, bit-identical, is such a change). The old names stay as
   aliases. The executor (`numba`, `cuda`) and the precision (`fp64`, `fp32`) are separate fields, recorded with
   every run and shown in every table, never part of the method name.
5. **Frame loss is judged from the raw data** (the pipeline's drops / gaps and the lost bead-frames in the run file),
   never from the GUI's display, which reads a 30 Hz snapshot and cannot slow the pipeline.
6. **User reports are HTML**, separate from `docs/results` (the project's own record, written for the next session):
   `docs/reports/<date>-<topic>.html` (+ `.ko.html`), generated by a tool from the run files and `report.json`
   like `tools/run_file_doc.py`: a one-line conclusion with the criteria, the conditions, the result tables
   (condition x method x executor: precision, accuracy, robustness, throughput, coloured), the figures, the invalid
   runs greyed with a one-line reason, and the data paths so the report can be regenerated.

## The criteria (the columns of every table)
- precision: the per-hold z and xy noise of stuck beads (nm);
- accuracy: the piezo staircase's step error raw and reference-corrected (median / max |error|, nm), the bias at the
  LUT ends;
- robustness: lost bead-frames (fraction), drops / gaps from the raw data;
- throughput: tracking ms per frame p50 / p99 / max (drops come from the tail);
- against the reference: the difference to `current_v1` numba FP64 on the same recorded frames - the LUT index
  jump rate and the z difference distribution (the offline comparison, the first gate, no rig time);
- tethered beads: the extension of a force ramp must be the same physical value.
The numbers that make a candidate the default (e.g. index jumps under 0.1 % of frames, under 5 nm after
interpolation when they happen) are the owner's; `current_v1` stays an option whatever the outcome.

## The bench list after this decision (design/bench-matrix.md)
The dimensions stay; the z method gains versions, the executor gains the precision; new blocks: the offline
numeric comparison, the double-buffered pipeline before / after, the tethered-bead force ramp, the profile of the
per-frame cost outside the kernel (the 555 Hz drops). The runs shrink from the full product to two stages: the
method versions x executors are screened in one standard condition (90 Hz, 20 beads), the survivors are then
expanded over rate x bead count x ROI for the "zero-drop boundary" table (rate against usable bead count, the GPU's
own ceiling).

## Consequences for the code
- `track.Z_METHODS` and the kernels take the versioned names; `acq.start` / `retarget`, the run file's start event
  and `tracking_stages`, the GUI's Z-method box and the bench tools carry `z_method`, `executor`, `precision`.
- `gpu.py` gains the FP32 kernel (its own precision field); `test_gpu` keeps comparing the FP64 kernel to numba at
  1e-9 and gains the offline comparison of the FP32 kernel (jump rate, z difference) against the owner's limits.
- A double-buffered frame path (two streams) in the GPU executor, judged by the p99 / max before and after.
- `tools/offline_compare.py`: the same recorded frames through the reference and every variant.
- The HTML report tool and `docs/reports/`.
