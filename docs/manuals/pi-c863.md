# PI C-863.11 Mercury controller + M-126.PD1 magnet stage (GCS over serial)

## Purpose on the rig

Moves the permanent magnets up and down above the sample, which sets the force on the beads. The force is computed
from the magnet position (`Magnet2Force v3_for M270.vi` in the LabVIEW program). One linear axis, axis id `1`.

## Driver / SDK

- **LabVIEW path (what the program uses):** PI's LabVIEW driver `C:\Program Files\National Instruments\LabVIEW 2026\
  instr.lib\Mercury\GCS_LabVIEW\` - command VIs inside `Low Level\General command.llb` (`MOV.vi`, `VEL.vi`, `GOH.vi`,
  `POS?.vi`, `TMN?.vi`, `TMX?.vi`, ...) and `Mercury_GCS_Configuration_Setup.vi`. The only serial writer underneath is
  `PI Send String.vi`, over NI-VISA (V6: `docs/motor-call-site-census.md`, "Only FOUR VIs"). `MOV.vi` and `VEL.vi` send
  `ERR?` after the command, so each command costs two round trips (V6: `docs/motion-path-audit.md:47-52`).
- **Also installed, not used by the LabVIEW path:** PI Software Suite 2.4.0.3 (`C:\Program Files (x86)\Physik
  Instrumente (PI)\Software Suite\`), PI GCS library `PI_GCS2_DLL` 3.7.1.5 (`C:\ProgramData\PI\GCSTranslator\
  PI_GCS2_DLL_x64.dll`), PI USB drivers. A port can talk GCS ASCII directly over the serial port (as V6's scripts do)
  or through `PI_GCS2_DLL`.
- Vendor manual: PI C-863 Mercury user manual and the GCS command reference (in the PI Software Suite `Manuals`
  folder).

## Units, signs and offsets

- Native unit **mm** (`POS?`, `MOV`, `SPA 0x15/0x30`).
- **0 mm = top of travel, magnets farthest from the sample**, at the negative limit switch that `FNL 1` seeks. The
  number grows **downward, toward the sample**; a larger value means a larger force (user observation at the rig,
  2026-09-27; V6: `docs/motor-limit-assurance-plan.md` "The envelope").
- After a controller power cycle the counter reads 0 **wherever the stage happens to be**: 0 is the limit switch only
  after a reference move.

## Safety envelope and what to restore after a job

| item | value | source |
|---|---|---|
| development envelope | **0 .. 39 mm**, enforced by the controller: `SPA 1 0x15 39`, `SPA 1 0x30 0` (TMX / TMN) | `third_party/mt_labview/tools/bench/motor_limits.json` `pi`; RULES.md section 3 |
| session start (V6 gate) | set TMN/TMX and read back; `SVO 1 1`, `RON 1 1`, `FNL 1`; require `FRF?` 1 and `POS?` 0; verify `MOV 1 2` and `MOV 1 0` within 0.05 mm | V6: `tools/motor_send_pi.ps1` mode `limits-set` |
| session end (V6 gate) | `MOV 1 0` (magnet to the top) and verify, **then** release the limits to TMN 0 / TMX 52 and read back | V6: `tools/motor_gate.py` docstring "MAGNET RETURN", `motor_limits.json` `release_hi_mm` 52 |
| the original's own limit | the panel control `Trans Step (mm)` (an absolute target despite its name) has a Data Entry range 0 .. 40.84 mm; `Max Trans Pos.vi` returns 40.94. Nothing clamps a value in front of `MOV` | V6: `docs/motor-limit-assurance-plan.md` "P2 live findings" |

After every job: the magnet at 0 mm, TMN 0 / TMX 52 read back (the controller's state after a power cycle), port closed.
Cleanup failed -> keep the lock and report (RULES.md section 2.5). Motion during development only through the approved
gate (today V6 `tools/motor_gate.py`).

## Known pitfalls

1. **The soft limits live in RAM.** A controller power cycle resets TMX to 52 and drops the reference. Never `WPA`.
2. **After a power cycle the servo is off** (`SVO?` 0) and every `MOV` answers ERR 5 without moving - this looked like
   "PI does not respond" on 2026-09-23. Send `SVO 1 1` first.
3. **Writing `SPA 0x15/0x30` leaves the axis unreferenced** (`FRF?` 0), and every `MOV` then answers ERR 5 before the
   limit is consulted (V6: `tools/bench/motor_gate2_live.log`). Reference after setting limits.
4. **The original does not reference.** With `Autoreference?` = 0 it uses `RON 1 0` + `POS 1 <z>`, i.e. it *declares*
   the position. After a power cycle that cements a false zero: on 2026-09-23 a `MOV 1 30` stopped at 22.2 mm with
   ERR 216 (hard limit; V6: `tools/bench/pi_testmove_20260923e.log`). Use a real reference move (`FNL 1`).
5. **Check `ERR?` after every command.** `MOV 1 0` while already at 0 but unreferenced was rejected with ERR 5 and the
   position alone still looked "reached".
6. **The panel limit coerces typed values only.** Values written by local variables, VI Server or wires pass unclamped;
   a program must clamp in code (or rely on TMN/TMX).
7. A single lost reply costs the VISA timeout (5000 ms in the LabVIEW driver); keep serial traffic off the frame
   acquisition path (RULES.md section 3, rule 6 of CLAUDE.md).
8. Strings in the VI such as `M-126.PD1, COM4 9600` / `M-126.PD1, COM5 115200` are a legacy selection ring for other
   rooms, **not** this machine's ports (V6: `docs/instrument-libraries.md:189-226`).

## Parameters read from the controller (2026-10-25, read only; V6 cards pistall / pistall2)
- `CST?` 1 = `6234-9-4102` (an id, not a model name; the stage model stays unknown).
- `0x8` Maximum Position Error = **1.0 mm** (stall: above it the controller switches the servo off, error -1024).
  Kept at 1.0 mm (owner 2026-10-26, decision 0020).
- `0xA` maximum closed-loop velocity 50 mm/s; `0x49` velocity 15; `0xB` / `0xC` acc / dec 300 mm/s^2 (maxima `0x4A`
  / `0x4B` 500).
- Travel: `0x2F` reference -> positive limit 51.5 mm; `0x17` negative limit -> reference 0.5 mm; `0x63` limit -> hard
  stop 0.1 mm.
- Data recorder (`HDR?`): DRT 0 = default; record options 1 commanded position, 2 actual position, 3 position error;
  triggers 1 and 6 = any position-changing command; 2 tables x 1024 points. `DRR?` on an empty table answers ERR 17.
  Not used (no DRT write; the recorder setting would persist in RAM into LabVIEW sessions).
- Normal following lag, POS? polled every ~2.8 ms against the ideal trapezoid at 15 mm/s: max about **0.05 mm**
  (+-0.02) at the end of acceleration, 0.02-0.05 mm at constant speed (one slow 16 ms sample gives 0.15 +- 0.12).
