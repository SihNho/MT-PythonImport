# Arduino frame divider (JAI -> iXon trigger)

## Purpose on the rig

Decision 0005: the JAI camera is the only master clock. An Arduino UNO-compatible board counts the JAI's exposure
pulses in hardware and, every N JAI frames, outputs a pulse k JAI frames wide that triggers one iXon frame (later
possibly also the OBIS modulation input). The PC sets N, k and checks the firmware version **only at setup and at the
end**; during a run there is no PC communication. The wiring exists; it has never been run.

```
JAI Line1 (TTL out, "Exposure Active") --> Arduino D5 (Timer1 external clock T1)
Arduino D9 (Timer1 output OC1A, hardware PWM: high for k counts every N counts) --> iXon EXT TRIG
```

## Driver / SDK

- No SDK. Firmware is built with **Arduino IDE 2.3.10** (installed, `C:\Program Files\Arduino IDE\`).
- **The frame-divider firmware does not exist yet.** `G:\Codes\Arduino` holds two bench sketches only:
  - `SwitchCounter/SwitchCounter.ino` - reads pin 2 (`INPUT_PULLUP`) in the main loop, mirrors it on pin 3 with
    `analogWrite`, counts rising/falling edges in software, Serial 9600 (prints commented out);
  - `Pulse generator/PulseGen/PulseGen.ino` - a 10 Hz square wave on pin 4 (`delay(50)`).
  Neither uses D5/D9 or Timer1, and software edge counting in `loop()` can miss pulses at 150 Hz with serial traffic.

## Firmware interface still to be designed (decision 0005, not a command table)

Required, not implemented: set N and k; report the firmware version (the board's identity); report the 32-bit JAI
count and the number of EMCCD triggers issued; reset the count to 0 when JAI pulses stop (timeout); the watchdog. The
PC sends these only at setup and at the end of a run.

## Planned outputs (light gating)

Not designed or built yet; this section records what the decisions require of the board.
[Decision 0005](../decisions/0005-camera-sync.md) already foresees the OBIS modulation input on the trigger line;
[decision 0013](../decisions/0013-mt-tirf-extensible-illumination.md) and
[ui-requirements.md](../spec/ui-requirements.md) U24 extend the board to gate the excitation light per EMCCD frame.

- **Per-frame gating from the illumination sequence.** The sequence has one column per laser or shutter and one row
  per EMCCD frame, in three parts: a header (once), a body (repeated) and a footer (once). The PC loads it into the
  firmware at setup, with N and k; during the run the board steps through it on each EMCCD trigger and sets one TTL
  output per light. Example: 532 nm on every frame (smFRET), or 637 nm on 1 frame in 10 as a FRET correction / Cy5
  presence probe (U28, U36).
- **Nothing is timed by the PC.** The outputs change only on the JAI-derived count, like the D9 trigger; the PC does
  not talk to the board during a run (0005). The sequence **actually executed** (with the firmware's count of
  triggers) is read back at the end and stored in the data file's metadata ([hdf5-v1.md](../format/hdf5-v1.md)).
- **Back-ends (one interface, three options, owner 2026-10-23, choice open):** mechanical shutter, AOM, or laser
  modulation (e.g. OBIS digital modulation; whether each OBIS unit accepts it is still to be checked in
  [coherent-obis.md](coherent-obis.md)). The TTL sequence is the same; the device settings differ (shutter open /
  close delay; AOM TTL polarity and analog power level; laser modulation mode and power).
- **Switching-time check before a run.** The program compares the chosen back-end's switching time (mechanical:
  ms; AOM: µs; laser modulation: µs to tens of µs — typical figures, to be measured on the actual hardware) with the
  gap between EMCCD frames, and warns or refuses, e.g. fast per-frame alternation with a mechanical shutter.
- Outside recording all lights are closed by default (photobleaching, U24); manual open / close for alignment goes
  through the same outputs.
- **Open:** pin assignment for the light outputs (which pins, how many lights, whether they can share Timer1 timing
  with D9 or are set in the trigger interrupt), output levels for each back-end's input, and the back-end choice.

## Units, signs and offsets

- N and k are in **JAI frames** (buffer numbers), not in time. EMCCD frame m belongs to absolute JAI buffer numbers
  [mN, (m+1)N) (decision 0005).
- The Arduino clock's accuracy does not matter: it only counts; it times nothing except the "pulses stopped" timeout.

## Safety envelope and what to restore after a job

- No motion. The Arduino is a rig device: the rig lock applies (RULES.md section 2).
- **Never open the port during a run** - the auto-reset clears the counter.
- After a job: port closed; record N, k and the firmware version used in the run record.

## Known pitfalls

1. CH340 boards have no serial number; two boards look the same to Windows. Ask the firmware who it is.
2. Opening the port resets the board; wait for the bootloader (~2 s) before the first command.
3. A UNO's D9 is a 5 V output; check the input range of the iXon EXT TRIG and the OBIS modulation input.
4. The JAI must run at a fixed period (auto exposure off) or the master period changes (decision 0005).

## Open questions for the owner

1. Which board exactly (UNO clone with CH340?) and where is it plugged in?
2. The JAI Line1 output voltage and pulse width at 90 / 150 Hz - an oscilloscope check is listed in decision 0005.
3. Which edge marks a frame: the start of `Exposure Active` (rising) or its end?
4. The iXon trigger mode, which decides whether k sets the exposure (External Exposure) or only the start (External).
